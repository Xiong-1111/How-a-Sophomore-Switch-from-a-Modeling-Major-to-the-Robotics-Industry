# Benchmark 与任务判定

本笔记说明什么是 **Benchmark（基准评测）**、什么是 **判定**，以及如何把天工 2 的「左手抓苹果放进篮子」判定脚本，移植到天轶 2。

## Benchmark

**Benchmark** 是一套客观、统一的评测体系。  
例如要测「机器人会不会把苹果放进篮子」，不能只靠主观观看，而需要固定标准。

一套完整的 Benchmark 通常包含：

| 组成 | 含义 | 本任务中的例子 |
|------|------|----------------|
| **任务** | 要完成什么 | 左手抓苹果，放进篮子 |
| **场景** | 在什么环境里做 | 桌子、苹果、篮子、天轶 2 站在桌前 |
| **输入 / 输出** | 给模型什么、它应产出什么 | 观测、动作；最终物体位置变化 |
| **成功判定** | 程序如何认定“完成了” | 苹果的 AABB 落在篮子内部 |
| **评价指标** | 除成败外还看什么 | 成功率、耗时、是否碰撞等 |

以上几项合在一起，就可以构成 Benchmark 的一部分。

## 判定

**判定**是程序根据预先写好的条件，自动判断「这件事有没有完成」。

它不是人眼看视频，而是例如：读取苹果、篮子的位姿 / 包围盒，检查苹果的 **AABB（轴对齐包围盒）** 是否落在篮子内部；满足则成功，否则失败。这样才能保证每次评测用同一套规则。

# 任务一：天轶 2.0 + 强脑手（左手抓苹果放进篮子）

参考脚本：`tasks/TienKung2_Station_tasks/TienKung2_Station_task_02.py`  
目标：把该判定逻辑移植到 **天轶 2（TianYi2）**。

一共有六步：

1. **检查场景**  
   确认有桌子、苹果、篮子；天轶 2 站在地板上并面向桌子；左手在桌面上方，便于抓取。缺物体或站位不对，判定写对了也可能一直失败。

2. **写新任务配置**  
   把天工 2 toml 里的 **`[robot]`** 改成天轶 2 的信息（机型路径、名称、关节/手部等），让仿真加载天轶 2 + 强脑手。

3. **拷贝判定工具**  
   沿用「苹果 AABB 在篮子里面」：计算苹果的轴对齐包围盒，判断是否落在篮子有效区域内，与天工 2 任务标准一致。

4. **让天轶 2 基类能做判定**  
   在 `TianYi2_Brainco2_task_base.py` 中补上判定接口/逻辑，派生任务类直接调用，不必每个任务重写。

5. **新建 04 任务类**  
   复制 `TianYi2_Brainco2_ind_task_01.py`，改三处：  
   - 注册名和类名改为  
     `@Registry.register("TianYi2_Brainco2_ind_task_04")`  
     `class TianYi2_Brainco2_ind_task_04(TianYi2_Brainco2_Task_Base):`  
   - 读取当前场景中苹果和篮子的路径  
   - 接入 AABB 判定（任务结束或每步检查时调用）

6. **挂到入口，避免 Task not found**  
   在 `__init__.py` 中 import `TianYi2_Brainco2_ind_task_04`，让类加载时登记进 `Registry`。  
   在 `benchmark.py` 中加入 `ind_task_04`，否则会出现 `Task name ind_task_04 not found`，仿真空转。  
   （文件名是 `__init__.py`，前后各两个下划线。）

# 任务二：天工 3.0 + 强脑手（左臂从传送带拿开关零件放入托盘）

参考脚本：`tasks/TienKung3_Brainco2_tasks/TienKung3_Brainco2_task_01.py`  
目标：移植到目标仓库中的 **天工 3（TienKung3）**。

核心抓取逻辑不必重写，但要适配目标仓库的 **任务接口、场景路径、日志 / 评测参数**，并修掉源场景里开关的刚体问题。

## 一、最初问题：开关从机器人头顶掉落、复位后再掉

开关会出现在机器人头部上方，落下后又复位、再掉。排查 USD 后有两类原因。

**1）与传送带初始穿透，且保存了异常速度**

- 开关与传送带重叠：传送带顶部 \(Z \approx 1.0380\)，开关最低点 \(Z \approx 1.0316\)。PhysX 启动时会强制分开重叠碰撞体，开关被弹飞。
- USD 里还存着很大的初始运动：线速度约 \((0.025,\ -0.030,\ -0.00008)\)，角速度约 \((58.7,\ 82.9,\ 2.2)\)。

**2）最外层被设成「无碰撞的动态刚体」**

- 外层坐标系会单独受重力
- 外层坐标与真实开关主体不同步
- 任务读的是外层坐标，而不是 `E_body_16`

**修改：**

1. 把开关位置上移，避免与传送带穿透  
2. 启动时清零线速度、角速度，去掉 USD 里保存的异常运动  
3. 复位时同时恢复姿态并清速度  
4. 移除外层的 **Rigid Body API**，避免无碰撞的坐标轴自己自由落体  

## 二、移植问题：新旧 Benchmark 流程不兼容

源仓库天工 3 用的是旧流程：

> 状态 JSON + 固定本机 ZMQ（端口固定，通常通信地址直接写死）+ 本地成功率统计

目标仓库用的是新流程：

> 任务握手 + episode + envelope ZMQ（消息包的外层封装）+ 跨机配置 + RGBD 录像 + 进程超时管理

录像的作用：发观测时带上相机帧，方便事后查看机器人成功 / 失败原因。

需要处理下面 5 处不兼容。

**1. 构造参数与 ZMQ 地址不同**

两边任务接口不一致。目标仓库构造函数多了：

| 参数 | 含义 |
|------|------|
| `episode_id` | 第几次任务运行 |
| `task_name` | 当前任务名 |
| `condition` | 实验条件（主要作日志标签，并保持接口兼容） |
| `baseline` | 当前用哪种控制算法 / 策略 |
| `seed` | 随机种子，便于复现 |

ZMQ 地址也不能再写死成本机固定端口，要按目标仓库的跨机配置来。

**2. 动作消息格式不同**

- 源：旧格式，大致只有 `topic` + `data`  
- 目标：**envelope**（外层封装），除动作外还有 `topic`、`payload`、`episode_id`、`step_id`、`timestamp`

**3. 观测格式不同**

- 源：只采一个头部相机 RGB，发送时没有 episode 信息  
- 目标：要 RGB、深度，并标注 `episode`、`step`，同时写入录像  

**4. 源工程没有目标录像流程**

源天工 3 基类没有 `EpisodeVideoRecorder`；目标仓库要求每个 episode 保存独立录像。

**5. 任务结束方式不同**

- 源：用 `status_file_path` 收尾  
- 目标：不会给天工 3 传入 `status_file_path`，而是通过 **episode 生命周期、ZMQ reset、TaskManager、录像释放** 管理结束流程
